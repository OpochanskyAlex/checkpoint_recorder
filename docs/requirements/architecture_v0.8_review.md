# Architecture Review Report

## Reviewed Versions

- **Architecture:** v0.8 (`architecture_v0.8.md`)
- **Business:** v0.5 (`business_analysis_v0.5.md`)
- **Context:** v0.7 (`system_analysis_v0.7.md`)

---

## 1. Executive Assessment

Architecture v0.8 is a materially improved document over v0.7. All ten mandatory revisions from `architecture_v0.7_review.md` are demonstrably addressed: AD-7 through AD-10 are now fully authored with alternatives and consequences, Flows F/G/H fill the three missing System v0.7 flow gaps, the backup architectural intent is defined, the Observability Collector failure contract is specified, and the ADR table now has no phantom references. The document is largely credible and actionable. However, two concrete gaps remain that create implementation-time ambiguity: the conversation state routing model is not specified (how does the Message Dispatcher distinguish disambiguation responses from periodicity selections from confirmation responses?), and the user-triggered Alert archiving transition appears in the Alert state model (System v0.7 §6) but has no corresponding command, flow, or component responsibility in the architecture. A third issue — the Scheduled Process run-lock mechanism — is required by the document but left architecturally unspecified. These are focused, resolvable gaps; the architecture is a strong baseline, but an implementation specification author would be forced to make unilateral decisions on each of these points if they remain unresolved.

## 2. Strengths

- **All v0.7 mandatory revisions are addressed.** AD-7 (cascade atomicity), AD-8 (archived metric alert suspension), AD-9 (ParseAttempt+prompt compensating delete), and AD-10 (async chart coroutine contract) are fully authored with alternative analysis, rationale, and consequences. No phantom ADR references remain.
- **Flows F, G, H fill the three System v0.7 flow gaps completely.** Account restoration (PendingDeletion → Active state transition, non-confirmation behavior), ParseAttempt late categorisation (Deferred list view, Entry creation path, discard path), and metric archival/reactivation (Active ↔ Archived transitions, AD-8 behavioral consequence) are now all modeled end-to-end.
- **AD-9 compensating delete is correctly specified.** The ParseAttempt Manager owns the compensation, the failure path is traced, and the operator detection mechanism via Observability is defined. The `try/finally` pattern guidance is implementation-appropriate.
- **AD-10 exception handling contract is explicit and correct.** Top-level exception handler in the coroutine, error message as second Telegram message on failure, `chart_delivery_failure_event` emission — these three together close the "silent async failure" gap identified in the previous review.
- **Observability baseline is production-grade.** `scheduler_heartbeat` is now separate from `scheduler_run_completed`, `observability_collector_health` self-heartbeat is defined, `active_users_count` freshness mechanism is specified (pushed on each Entry write), `chart_delivery_event` is separated from `chart_invocation_event`, and `alert_evaluation_event` now distinguishes `failed_after_retry` from first-attempt `failed`. This is above-average for a portfolio-scope architecture.
- **Repository-layer isolation testability strategy is concrete.** The requirement for a test-injectable repository interface and the specific assertion ("call every read operation with a mismatched user_id and assert empty result") turns a vague requirement into a testable contract.
- **raw_input log-boundary enforcement is structural, not convention-based.** The schema validation gate at the Observability Collector emission boundary is the right control — structural absence of free-text fields in approved schemas prevents PII leakage even if a developer inadvertently constructs a non-conforming event.
- **Backup architectural intent is defined and scoped appropriately.** Daily file export, RPO ≤ 24 h, RTO ≤ 4 h, deployed before first launch — this converts D-013 from an unmitigated architectural gap into a deployment obligation with defined bounds.
- **Open bot registration allowlist placeholder is correctly scoped.** A named check point in the User Session Guard as the single extension point is the right architectural pattern — it avoids structural changes when access control is introduced.
- **Re-registration of a Deleted user is now explicitly modeled.** Account Manager description and the Failure Scenarios table (§9) both cover the fresh InternalUser creation path with the uniqueness constraint implication called out.

## 3. Critical Weaknesses

- **The conversation state routing model is architecturally undefined.** The Message Dispatcher must classify incoming messages by intent, and the User Session Guard manages "per-user conversation state." However, the architecture defines no conversation state model. Multiple flows create "pending response" states — at minimum: (1) active ParseAttempt disambiguation prompt, (2) periodicity selection prompt (Flow A step 5 / Flow 7), (3) metric deletion confirmation prompt (Flow 11), (4) account deletion confirmation, (5) account restoration confirmation (Flow F), (6) metric archival/reactivation (Flow H). When a user sends a bare "2" or "yes," the Message Dispatcher must know which of these states is active in order to route the response to the correct handler. No formal conversation state machine is defined, no state is associated with the User Session Guard's state model, and no routing logic is described. Without this, an implementation specification author must design the conversation state machine from scratch — and every decision made there has behavioral consequences for multiple flows.

- **User-triggered Alert archiving has no architecture flow or handler.** System v0.7 §6 Alert State Model defines: "Archived | User archives alert" as a user-triggered exit from Active state. The same model defines the inverse (Archived → Active) transition as user-triggered. Flow 9 covers alert listing and individual deletion, but no flow, command, or component responsibility covers user-initiated alert archiving or alert reactivation. The Metric Manager description is limited to metric-level archival/reactivation. No component is assigned ownership of the user's "archive this alert" command. This is not a state that can only be reached via cascade — it is explicitly user-triggered and requires a handler.

- **Flow A (Standard Data Entry) collapses the periodicity sub-path into a single step without modeling the intermediate state.** Step 5 reads: "auto-create with periodicity prompt → Entry record write." In reality, these are two separate interactions: (a) metric auto-creation + periodicity prompt dispatch, then (b) user responds to periodicity prompt, then (c) Entry record write. Between (a) and (b), the user is in a "pending periodicity selection" state. If any other message arrives during this state, the system must decide: ignore it, queue it, or error. The architecture provides no guidance. The User Session Guard's described states (Active/PendingDeletion/Deleted, one-active-ParseAttempt) do not include "pending periodicity selection." This creates an unmodeled user state that is not an edge case — it is the normal path whenever a user logs a metric for the first time.

## 5. Trade-off & ADR Issues

- **AD-2 (Polling vs. Webhook) is correctly deferred but the health check coupling note remains unresolved.** The document acknowledges the coupling ("if polling is chosen, the health check cannot be an externally callable HTTP endpoint") and gives two options without deciding. This is not a new issue — it was partially addressed in v0.8 by adding the coupling note — but it remains an open configuration branch that blocks process supervisor design. An implementation specification author will need a decision here.

- **Metric name uniqueness enforcement layer is not explicitly decided.** The Data Strategy (§6) says "Consistent name-uniqueness per user" is a consistency need for Metric, and §7.1 states "Upsert or unique-constraint-on-Telegram-ID at Data Repository layer" for InternalUser registration. But for Metric name uniqueness per user, no equivalent statement exists. Is this enforced at the database layer (unique constraint on `(internal_user_id, metric_name)`) or at the application layer (Metric Manager queries before insert)? Application-layer uniqueness check is vulnerable to the same "miss one call" problem that motivated AD-5 for user isolation. The decision should be explicit.

- **AD-9 compensating delete — the 30-second detection window is hardcoded in Flow B without being configurable.** Flow B states: "detected via Observability Collector: `parse_attempt_event` with status=Pending and no subsequent `prompt_dispatched` event within 30 s." This 30-second window is an operational monitoring threshold. It is not mentioned in the Configuration & Secrets component, not listed in §13.2 open questions, and has no SU-xxx tracking. Either it should be a configurable parameter or the rationale for the 30-second fixed value should be stated.

- **Compound first-contact flow (onboarding + simultaneous data entry) is mentioned in the Account Manager component description but has no architecture flow.** System v0.7 Flow 1 step 4 defines this as a distinct transactional scenario with explicit partial-failure semantics. The Account Manager correctly documents the failure behavior ("user is registered but entry intent is lost") but the interaction among Account Manager, Entry Processor, NLP Parsing Engine, and Message Dispatcher for this compound case is not modeled as a flow. This is an underspecification that leaves the implementation free to interpret the sequencing.

- **Token authentication failure post-detection behavior is not defined.** §10 correctly specifies that a `token_auth_failure_event` is emitted. The Configuration & Secrets component description says "failure emits a specific event." But the behavioral consequence is not stated: does the Telegram Gateway retry, halt, raise to the process supervisor, or continue in a degraded state? A token failure is not recoverable without operator intervention; specifying "halt and emit alert" vs. "retry with backoff" has direct availability implications.

## 11. Mandatory Revisions

1. **Define a conversation state model for the User Session Guard.** Enumerate the named pending-prompt states that affect message routing: at minimum `Idle`, `PendingDisambiguation` (active ParseAttempt), `PendingPeriodicity` (awaiting periodicity selection after metric auto-create or explicit create), and any confirmation-pending states (account deletion, metric deletion, account restoration). State that the Message Dispatcher consults this model before routing. State the behavior when a new message arrives during each non-Idle state. This single addition resolves three separate gaps: the conversation state routing ambiguity, the periodicity-pending state gap in the User Session Guard, and the Flow A periodicity sub-path compression.

2. **Address the Alert Archived state traceability gap.** Either: (a) add user-triggered alert archiving and reactivation to Flow 9 (extend to "Alert Listing, Archival, Reactivation, and Deletion") with the responsible component (Metric Manager or a dedicated Alert Manager), or (b) add an explicit note stating that user-triggered alert archiving is out of scope for this architecture version and the corresponding System v0.7 state transition is deferred, with the justification. The current state — where a named entity state in the System document has no architectural handler — will cause implementation confusion.

3. **Specify the Scheduled Process run-lock mechanism at a conceptual level.** Name the approach (e.g., "a `scheduler_lock` record in the Data Repository with an atomic check-and-set on invocation start and a release on invocation end; lock acquisition failure emits `scheduler_overlap_event` and aborts"). The specific technology can remain deferred to AU-003, but the pattern must be named. "Must prevent concurrent overlap" is a requirement; the mechanism to satisfy it is an architecture decision.

4. **Add a behavioral note to Flow C (Account Deletion) for active Pending ParseAttempts.** State what happens to any active Pending ParseAttempt when the account transitions to PendingDeletion. The recommended behavior: ParseAttempt Manager is notified by Account Manager and transitions the active Pending ParseAttempt to Deferred before the PendingDeletion transition completes. If no active ParseAttempt exists, this step is a no-op. This should be an explicit step in Flow C, not left to implementation.

5. **Define or defer the periodicity prompt expiry.** State whether a pending periodicity selection prompt expires (and if so, what the timeout is, which configurable parameter controls it, and what the cleanup mechanism is) or persists indefinitely (and if so, state the implications for user state accumulation). If it persists indefinitely, add it to the Scheduled Process cleanup scope or explicitly state it does not require cleanup. This is required to close the abandoned periodicity prompt accumulation gap.

## 12. Iteration Recommendation

**Iterate (Targeted Architecture Fixes Required)**

The document is close to "Accept with Minor Adjustments" — the v0.7 mandatory revisions are all addressed and the overall structure is strong. However, the conversation state routing gap (Mandatory Revision 1) is a genuine implementation blocker: an implementation specification author cannot deterministically route incoming messages to the correct handler without a conversation state model, and the decision has behavioral consequences across at least six flows. The Alert archiving traceability gap (Mandatory Revision 2) is a clean yes/no decision that should be made at the architecture level rather than left to the implementation. Mandatory Revisions 3–5 are targeted and bounded. None of the remaining revisions require a structural rethink — all five can be addressed as additive specifications to the existing document without changing any component boundaries, ADRs, or flow structures.
